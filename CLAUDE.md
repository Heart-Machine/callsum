# Договорённости по проекту

Файл для Claude Code: он читается автоматически в начале каждой сессии. Здесь собрано то,
что иначе пришлось бы повторять каждый раз.

## Как ведём работу

- **Каждая задача — своя ветка.** Прямые коммиты в `main` запрещены и технически невозможны:
  ветка защищена, изменения попадают туда только через pull request.
- **Готово — значит есть PR.** В описании три вещи: что изменилось, как проверить у себя,
  на что обратить внимание. Черновой PR открывается рано, чтобы правки было видно по ходу.
- **Сливает владелец репозитория** кнопкой на GitHub, после проверки. Claude не сливает.
- **Тесты обязаны быть зелёными** — это требование настроено в защите ветки. Автопрогон
  идёт на Windows: тесты разбирают пути Windows и реестр.
- **После слияния ветка удаляется.** На GitHub — сама: в настройках репозитория включено
  «Automatically delete head branches». Локальные копии подчищает разработчик:

  ```
  git switch main; git pull; git fetch --prune; git branch -d имя-ветки
  ```

  `git fetch --prune` убирает ссылки на удалённые ветки, которых уже нет на GitHub.
  Если PR слит через squash, git не считает ветку слитой и откажется её удалять —
  тогда `git branch -D имя-ветки`.

## Команды для пользователя — в синтаксисе PowerShell

Терминал у владельца проекта — Windows PowerShell 5.1. Там **нет операторов `&&` и `||`**:
скопированная команда с `&&` падает с ошибкой про недопустимый разделитель. Поэтому всё,
что предлагается запустить вручную, пишется через `;`, а при необходимости — через
`if ($?) { ... }`. Строка в программу передаётся конвейером из одинарных кавычек:

```
'{"cmd":"doctor","id":"1"}' | .\dist\callsum-core\callsum-core.exe serve
```

## Что не попадает в репозиторий

Личное и машинно-зависимое остаётся на машине:

- `config.toml` — в `.gitignore`; в репозитории только `config.example.toml`, из которого
  программа создаёт личный файл при первом запуске;
- `recordings`, `out` — записи созвонов и результаты;
- `.venv`, `dist`, `build` — окружение и сборки.

Перед первым пушем в новый репозиторий проверяются абсолютные пути, имя пользователя
Windows, почта и токены. Коммиты подписаны адресом `@users.noreply.github.com`, личная
почта в историю не уходит.

## Настройки чужих программ

Если для работы нужно изменить настройки стороннего приложения — заводим **отдельный
профиль**, а общие настройки пользователя не трогаем. В OBS это профиль и коллекция сцен
`callsum`, которые создаёт `callsum obs-setup`; приложение переключается на них перед
записью и возвращает прежний профиль после. Файл настроек, который правим, копируем рядом
(`.bak`) перед изменением.

## Язык

Комментарии, сообщения коммитов, документация, интерфейс и тексты ошибок — по-русски.
Имена файлов, функций и веток — латиницей.

Исключение: **в `requirements*.txt` комментариев по-русски быть не должно.** pip 24,
который идёт в свежем виртуальном окружении, читает эти файлы в кодировке консоли и падает
с ошибкой декодирования.

## Проверка работы

Тесты — необходимое условие, но не достаточное. В этом проекте живой прогон находил то,
чего тесты не видели: собранное ядро печатало служебное сообщение в поток протокола,
PowerShell дописывал метку кодировки в начало команды, приложение продолжало обрабатывать
запись вдвоём с другим своим экземпляром. Поэтому изменение считается проверенным, когда
оно прогнано на настоящей записи или в настоящем окне, а не только под `pytest`.

Тесты при этом не должны трогать реальные данные пользователя: окно запускается в
невидимом режиме (`tests/conftest.py`), а регистрация в реестре в тестах идёт под своим
идентификатором.

## Как устроен проект

- `callsum/` — ядро: запись через OBS (`obs.py`, `obsws.py`), извлечение дорожек (`audio.py`),
  распознавание (`transcribe.py`), склейка реплик (`merge.py`), протокол (`summarize.py`),
  конвейер (`pipeline.py`), окно (`gui.py`), режим мотора для внешнего приложения (`serve.py`).
- `prompts/` — шаблоны протоколов, обычные текстовые файлы.
- `packaging/` — сборка ядра в exe через PyInstaller.
- `docs/plan.md` — план второй версии (приложение на WinUI 3) и принятые по нему решения.

Рабочие команды:

```
.venv\Scripts\python.exe -m pytest tests -q      тесты
.venv\Scripts\python.exe -m callsum doctor       проверка окружения
packaging\build-core.cmd                         сборка ядра в dist\callsum-core
```

## Стиль кода

- Комментарий объясняет **почему** так сделано, а не пересказывает код. Если решение
  неочевидное или было принято после ошибки — причина записывается рядом.
- Сообщение об ошибке говорит пользователю, что делать дальше, а не только что случилось.
- Если поведение было исправлено — на него пишется тест, который падает на прежнем коде.
